# Заметки: системный дизайн

Кэширование: сначала спрашиваем, что именно медленно — чтение из базы или вычисление. Для горячих данных используем Redis со стратегией cache-aside: приложение читает кэш, при промахе идёт в базу и записывает результат с TTL. Инвалидация при записи — удаляем ключ, а не обновляем, чтобы не получить гонку двух записей.

Очереди сообщений нужны, когда отправителю не нужен немедленный ответ: письма, уведомления, обработка платежей после подтверждения. В ФинБанке мы использовали RabbitMQ: около двух миллионов сообщений в день, подтверждения доставки (ack) и очередь мёртвых писем для сообщений, которые не обработались за три попытки.

Идемпотентность платежей: каждый запрос на списание несёт ключ идемпотентности, сервер хранит результат по ключу 24 часа. Повтор запроса после таймаута сети возвращает тот же результат, а не списывает деньги второй раз.

Масштабирование чтения: реплики PostgreSQL для отчётов, основная база — только для записи и критичного чтения. Задержка репликации обычно меньше секунды, поэтому экраны «после оплаты» читают из основной базы, чтобы пользователь сразу видел новый баланс.

Наблюдаемость: метрики в Prometheus, дашборды Grafana, трассировка запросов через OpenTelemetry. Алерты — по симптомам (доля ошибок, задержка p95), а не по причинам вроде загрузки процессора.

Rate limiting на API: алгоритм token bucket в Redis, лимит на пользователя и на IP. При превышении — ответ 429 с заголовком Retry-After, клиент повторяет запрос с экспоненциальной задержкой.
